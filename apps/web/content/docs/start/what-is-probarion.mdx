An owner puts USDC in a vault, a NEAR contract of their own, and signs mandates from their own wallet: who gets paid, how much per payment and in total, how many times, until when, and above what amount a person must approve. The agent gets one key that can call `spend` and nothing else.

Testnet today, and one small vault on mainnet. [Testnet and mainnet](/docs/start/testnet-and-mainnet) says what differs between the two.

## The problem it solves

Giving an AI agent a wallet means trusting a prompt with money. Probarion moves the rule into a NEAR contract.

The limit sits on the money's path, not in a prompt or in the agent's own process. Even if every line of off-chain code were wrong, the vault refuses a payment outside its mandate. A payment made through the SDK passes these layers, in this order:

<Flow>

1. **Model proposes** A private model on NEAR AI Cloud may advise. It is optional and cannot widen a mandate. On testnet, the Canary's ledger of 2026-11-10, published in the repository, holds two of its attested decisions, which pass A1 to A7 offline and, on 2026-11-11, O1 and O2 online ([evidence](https://github.com/probarion/probarion/blob/main/docs/evidence/canary-vault/README.md#the-signed-ledger-published-2026-11-11), [online output](https://github.com/probarion/probarion/blob/main/docs/evidence/canary-vault/verify-online-2026-11-11.txt)). The testnet demo vault's ledger holds five more, made by Payables, which pass A1 to A7 offline; four of them, entries 10 to 13, also passed O1 and O2 online on 2026-11-12. The code allowed the last two of them, and the vault paid both invoices ([evidence](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/README.md#2026-11-12-payables-pays-on-its-own-with-an-attested-model), [the second](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/README.md#2026-11-12-filmed-a-second-invoice-paid-on-its-own-freeze-and-unfreeze), [online output](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/verify-online-2026-11-12.txt)). The TEE measurement is not pinned, so they do not show which model image ran, and A8 was not run on the Canary's two; on the demo vault's five it passed on 2026-11-12, with the invoices committed in the repository ([output](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/verify-a8-2026-11-12.txt)).
2. **Code decides** `decide()` runs built-in rules that cannot be removed. The SDK signs the decision into the ledger before anything moves.
3. **Contract enforces** The vault checks the spend against its mandate, then pays, holds it for an approver, or refuses.
4. **Ledger records** The SDK signs every decision, refusals included, and the result of each spend it sends, each chained to the entry before it.
5. **Anyone re-checks** Once the owner publishes the ledger, the verifier ties each spend to exactly one decision in it.

</Flow>

The ledger is kept by the SDK, not required by the contract. The vault checks only the form of a spend's decision hash, not that a ledger holds the decision, so a spend sent with the agent key alone has no decision in the ledger, and [verifier check d](/docs/trust/verifier-checks#check-d) fails on it. That is the case today on `v0.probarion.testnet`: its 2026-11-01 smoke run sent spends with no SDK and no ledger, so a live verify of that vault prints `RESULT: FAIL`. On the testnet demo vault, `demo.vaults.probarion.testnet`, the console's Payables agent signed each decision into the ledger before its spend, so a live verify of it prints `RESULT: PASS`.

Some outcomes stay out of the ledger. A result entry that fails to write is skipped, and the outcome says `ledgerComplete: false`. An approver's later approve or reject, and the expiry of a hold, are recorded on chain, and no code writes them to the ledger. That last point is inferred: it follows from the code, and no test shows it yet.

[How one payment works](/docs/start/how-one-payment-works) follows one payment through these steps.

## The idea in four numbers

| Number | What it counts |
| --- | --- |
| 0 | Full-access keys on the vault. A public RPC call shows it. |
| 1 | Method the agent's key can call: `spend`. |
| 0 | Recipient arguments on `spend`. The payee comes from the mandate. |
| 9 | Checks anyone can run. Live, they read the chain. Offline, they check a snapshot, a saved file of a ledger and its chain data, against itself, so [take the snapshot yourself](/docs/trust/verify-a-vault#offline-is-not-live). |

The 9 checks belong to the verifier, which reads the record afterwards. They are not the 14 checks the vault runs on every spend before it pays. [Payment checks](/docs/concepts/payment-checks) lists the 14, and [verifier checks](/docs/trust/verifier-checks) lists the 9.

<Callout kind="key" title="The agent cannot name a payee.">

A forged invoice or a hijacked prompt can ask to pay anyone. `spend` has no field to put an address in, so the money can only go to a payee you signed. For a cross-chain payee, the vault builds the withdrawal memo itself, from the mandate. [Why spend has no payee](/docs/concepts/why-spend-has-no-payee) explains the design.

</Callout>

## The parts

| Part | What it is | Status |
| --- | --- | --- |
| Mandates | The owner signs each one from their own wallet: one payee (a NEAR account, or a Base or Solana address paid out through NEAR Intents), `max_per_payment`, `max_total`, `max_uses`, `expires_at_ns`, `approval_above`, and the one agent key that may use it. | Live |
| The vault contract | The owner's own contract. It holds the USDC, checks every spend against its mandate and a daily backstop (a cap on the total it pays or sets aside in one UTC day, fixed when the vault is created), holds a spend above `approval_above` for an approver, and pays the mandate's payee. | Live |
| The factory | Creates vaults with no access keys. On testnet it is `vaults.probarion.testnet`. | Live |
| The agent key | A function-call key the vault adds to itself on the owner's instruction, limited to `spend`. | Live |
| The ledger key | A second function-call key, limited to `anchor`. The SDK signs every ledger entry with it and anchors the ledger root on the vault. | Preview |
| `@probarion/core` | `decide()`, the pure policy engine, plus the ledger and the verifier's checks a to i. No network, no file system. | Live |
| `@probarion/sdk` | The `Probarion` class, which runs one payment cycle with `process()`, plus the ledger stores, `snapshot()` and `verify()`. 0.1.1 is on npm. | Live |
| The `probarion` CLI | Prints each owner and approver transaction for `near-cli-rs` and signs none. It also makes agent keys, runs `check_spend` (the contract's free dry run of a spend) and runs the verifier. 0.1.1 is on npm. | Live |
| The web console | Wallet sign-in, vaults, mandates, keys, top-up, alerts, and Payables (the next row). It runs on testnet: open it with "Open console" in the site header. | Preview |
| Payables | The console's reference agent that pays invoices. It pays by itself only when an attested model confirms the amount the code read; without one, nothing is sent and the invoice waits for the owner. ## Who does what

- **The owner** signs every mandate, adds and removes agent keys and sets the ledger key, all from their own wallet. Without Probarion, the owner can also freeze the vault, unfreeze it, and withdraw its USDC and its NEAR Intents balance, the tokens it holds inside NEAR Intents to pay Base and Solana payees. Freeze takes no deposit. A mandate takes a storage deposit, and the vault sends back the excess. Most other owner methods need exactly 1 yoctoNEAR, which a function-call key cannot attach, so a dapp login key on the owner's account cannot call them.
- **Approvers** decide a held spend: approve sends the payment, reject releases the amount the hold set aside under the mandate. They are named when the vault is created, and no method changes them later.
- **The agent** asks to spend. Its key can call `spend` and nothing else, and only under the mandates that name that key.
- **Anyone** can read a vault on chain and run the verifier, with no account.
- **Probarion** runs the site and the console. If you use the console's Keys tab or Payables, Probarion generates the vault's agent and ledger keys on its server and stores each secret encrypted.

[Vaults, roles and keys](/docs/concepts/vaults-roles-and-keys) covers each role and key in full, and [mandates](/docs/concepts/mandates) covers every mandate field.

## What this does not do

- **It holds no owner key.** In the site's own words: "Non-custodial: Probarion holds no owner key." The agent and ledger keys the console makes are another matter: see [who does what](#who-does-what).
- **It cannot change the rules underneath the owner.** The vault has no upgrade method, no method to change the owner, and no full-access key.
- **It does not edit a mandate.** The payee is fixed when the mandate is created. A new payee needs a new mandate, and the owner can revoke the old one.
- **A vault's NEAR does not come back out.** The vault pays for its storage and its spends' gas from its own NEAR, and it has no method to withdraw NEAR. That NEAR is the vault's runway, and one plain transfer tops it up.
- **The contract does not judge whether a payment is wise.** It holds the agent to the limits the owner signed, and a spend above `approval_above` waits for a person. Off chain, `decide()` can still hold or refuse a payment the mandate allows, through its built-in rules, your own `custom.*` rules or an attested model's proposal.
- **It has no HTTP API that an agent pays through.** The console's invoice API answers only a signed-in owner or approver, on a same-origin request. An agent pays through the SDK, in its own process.
- **Some parts are not done yet.** On mainnet one small vault runs, with one NEAR payment and one Base payout, a test to the owner's own Base address, decided by code rules alone, and the mainnet factory is not deployed. No mainnet payment has been made on a model's proposal yet. On testnet, Payables paid two invoices on its own with an attested model on 2026-11-12, with test tokens ([the record](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/README.md#2026-11-12-payables-pays-on-its-own-with-an-attested-model), [the second](https://github.com/probarion/probarion/blob/main/docs/evidence/demo-vault/README.md#2026-11-12-filmed-a-second-invoice-paid-on-its-own-freeze-and-unfreeze)). It has not run on mainnet, and an unfinished payment stays marked "do not resend" until its reconcile job is built.
