How the page reads them:

- **Pinned views.** The three views, `get_config`, `view_access_key` and `view_account`, are read at the block of each spend, which the spend's own outcome names: for spend 2, `GM4ojam5J4e91NpzMF1BdbjF65wJcVPvbF6bijT37FTa` (height 224331722), and for spend 3, `B7iXoHCJHWLPWbLNispMCJBzSYC5oD8XqEuZr59MvWeB` (height 224358455). A later change to the vault cannot change their answers, and a check fails when an answer comes from another block.
- **Public hosts.** Every NEAR read asks FastNEAR's archival node, `archival-rpc.mainnet.fastnear.com`, then the regular node, `rpc.mainnet.fastnear.com`. The regular node forgets old transactions within days. The Base read asks `mainnet.base.org`. Each request gives up after 8 seconds and is tried up to twice more, when a retry can help, after 0.5 and 1.5 seconds, before the next host. An answer for another transaction, or one that is not final, goes to the next host. So a NEAR read takes at most 52 seconds, and the Base read 26.
- **Nothing in between.** The requests go from your browser to those hosts, with no cookies and no referrer, and none goes through Probarion's server. They change nothing and sign nothing.
- **Not the verifier.** The seven checks read the chain again, and check 06 hashes the two ledger entries the page carries for each payout. They do not check the entries' signatures or the rest of the file: the verifier does, see [Run the verifier](#run-the-verifier).

## How the payments were decided

### Spend 2: two refusals, then the code rules alone

The owner set up the run the same day:

- **A top-up through NEAR Intents 1Click.** The owner's wallet sent 1.5 native USDC to a 1Click deposit address ([transaction](https://nearblocks.io/txns/DWUMvM58dH3MpH9Jj838ycrfvCMjNJpgFsr43qu8u6mw)), and 1Click credited 1.499823 Base USDC to the vault's balance inside `intents.near` ([settlement](https://nearblocks.io/txns/FJA7rehnWXuMHeZkD1RBojqnEgAvkiJHtZtttCcDEUUU), signed by 1Click).
- **A ledger key.** `set_ledger_key` added `ed25519:RY7kjsaRStq4gt27RpNgErr9AjuKuZdzCXd6atSrzKK`, a function-call key on the vault that can call `anchor` and nothing else ([transaction](https://nearblocks.io/txns/CFhtVrCA3Cjumcx68kixLbR5r6Xo8Fp1PTueK8z968jb)).
- **Mandate 2.** The owner's own Base wallet, up to 1.00 USDC, 1 use, until 2026-11-20 ([transaction](https://nearblocks.io/txns/77cC8nMq6qWynU51FsPn8mkFAb3NEuDmEG7ZXjX6483g)).

Then the SDK ran three cycles on INV-M002. Cycles 1 and 2 each wrote one signed entry and anchored the ledger before the next cycle began. Cycle 3 wrote entries 2 and 3, then anchor 3:

| Entry | Time (UTC) | Who proposed | What code decided |
| --- | --- | --- | --- |
| 0 | 07:17 | `z-ai/glm-5.3-flash`, an attested model on NEAR AI Cloud, proposed `pay` with confidence 0.95 | Refused by the rule `mandate.payee_mismatch`. Nothing was sent |
| 1 | 07:22 | `Qwen/Qwen3.8-27B`, attested, proposed `pay` with confidence 0.9 | Refused the same way. Nothing was sent |
| 2 | 07:24 | No model | The code rules alone allowed it: all 14 rules passed |
| 3 | 07:24 | None: this entry records the payment | Spend 2, `burned`, transaction `BdN7oB76…rSQ9` |

**Why code refused the two proposals.** Both models proposed the right amount and the right Base address. Both also put the mandate's asset account, `base-0x833589fcd6edb6e08f4c7c32d4f71b54bda02913.omft.near` (Base USDC as a NEAR token), in the payee hint's `near_account` field. The SDK the owner ran, at commit `4ab41ca`, took any NEAR account in the hint as a contradiction for a mandate that pays a Base address (`payeeHintContradiction` in [`packages/core/src/policy.ts`](https://github.com/probarion/probarion/blob/4ab41ca/packages/core/src/policy.ts) at that commit). The rule's words in entry 0: "invoice names NEAR account base-0x833589fcd6edb6e08f4c7c32d4f71b54bda02913.omft.near; the mandate pays base:0xB22EAcDf11177d6D635E8956BBbBdd54B3E6EB27". The rule, as it ran, had no case for a Base mandate's own asset account, so both were false refusals: the amount and the Base address were right, and they cost two tries and no money. After the run, [PR #142](https://github.com/probarion/probarion/pull/142) changed the rule for a model's hint. In an invoice it is still refused. [Why spend has no payee](/docs/concepts/why-spend-has-no-payee#the-code-layer-refuses-a-contradicting-payee) explains the rule.

**Why the code rules alone decided the payment.** The owner ran the cycle a third time with no model. The SDK decided with the code rules alone, and every rule passed. Entry 2's body hash, `d64f0de77c38294cf103439e6b5b0c2623b96b114962afd50f5a3c553df2a336`, is the `decision_hash` the spend carries, so the spend points at its own decision.

### Spend 3: an attested model and the code rules

The owner set up the second round the same day, with one transaction:

- **Mandate 3.** The owner's own Base wallet, the payee of mandate 2, up to 0.25 USDC, 1 use, until 2026-11-20 ([transaction](https://nearblocks.io/txns/4cmSz4b3zHeWnbcw3HU6RJJ6afZa9zysu4SptE7mXT3T)).

| Entry | Time (UTC) | Who proposed | What code decided |
| --- | --- | --- | --- |
| 4 | 11:40 | `z-ai/glm-5.3-flash`, an attested model on NEAR AI Cloud, proposed `pay` with confidence 0.92 | Allowed, decided by `model+rules`: all 16 rules passed |

**What the attestation shows.** Before the SDK counted the answer, it checked the model's evidence: the signature, the response, the recorded proposal and the attestation report agree with each other and with ledger position 4 (A1 to A7), and the request matches the invoice text (A8). Entry 4's body hash, `d3807956b1e0a0481656862a50a2147d2b0a1f04834a30829529311c9cec32aa`, is the `decision_hash` spend 3 carries. ## What this does not do

- **They are tests, not customer payments.** Two payouts, of 1.00 USDC and 0.25 USDC, went to the owner's own Base wallet: one decided by the code rules alone, one proposed by an attested model and allowed by the code rules. They show the cross-chain path works on mainnet for this vault. They do not show a business paying a supplier.
- **By 2026-11-13, one mainnet payment had come from a model's proposal.** Spend 1 of 2026-11-11 was sent without the SDK, spend 2 was decided by the code rules alone, and spend 3 was proposed by an attested model and allowed by the code rules.
- **The model hint fix came after spend 2's run.** After it, [PR #142](https://github.com/probarion/probarion/pull/142) changed `payeeHintContradiction`: in a model's hint, a Base or Solana mandate's own asset account names no other payee. In an invoice it is still refused. Spend 2's run used the code before it, at commit `4ab41ca`. Spend 3's run used commit `c85f41b`, which holds it, but its hint named no NEAR account, so the change was not exercised.
- **The attestation does not show which model image ran.** A1 to A8 passed on entries 0, 1 and 4, and a later read-only run of `verify --online` passed O1 and O2 on all three ([output](https://github.com/probarion/probarion/blob/main/docs/evidence/mainnet-v0/s2-2026-11-13/verify-online-2026-11-13.txt)). The TEE measurement is not pinned, so the record does not show which model image ran.
- **The contract checks the burn, not the arrival.** The vault's part ends with the burn on NEAR. The POA bridge releases the USDC on Base, and check 07 reads that from Base.
- **No console or proof page serves this vault.** Both serve testnet. The mainnet factory is not deployed, so the console cannot create a mainnet vault yet.
