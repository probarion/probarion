How the page reads them:

- **Pinned views.** Both views, `get_config` and `view_access_key`, are read at the block of spend 2, `GM4ojam5J4e91NpzMF1BdbjF65wJcVPvbF6bijT37FTa` (height 224331722), which the spend's own outcome names. A later change to the vault cannot change their answers, and a check fails when an answer comes from another block.
- **Public hosts.** Every NEAR read asks FastNEAR's archival node, `archival-rpc.mainnet.fastnear.com`, then the regular node, `rpc.mainnet.fastnear.com`. The regular node forgets old transactions within days. The Base read asks `mainnet.base.org`. Each request gives up after 8 seconds and is tried twice more, after 0.5 and 1.5 seconds, before the next host.
- **Nothing in between.** The requests go from your browser to those hosts, with no cookies and no referrer, and none goes through Probarion's server. They change nothing and sign nothing.
- **Not the verifier.** The seven checks read the chain again. Whether the anchored ledger holds this spend's decision needs the ledger file, which the verifier reads: see [Run the verifier](#run-the-verifier).

## How the payment was decided

The owner set up the run the same day:

- **A top-up through NEAR Intents 1Click.** The owner's wallet sent 1.5 native USDC to a 1Click deposit address, and 1Click credited 1.499823 Base USDC to the vault's balance inside `intents.near` ([transaction](https://nearblocks.io/txns/DWUMvM58dH3MpH9Jj838ycrfvCMjNJpgFsr43qu8u6mw)).
- **A ledger key.** `set_ledger_key` added `ed25519:RY7kjsaRStq4gt27RpNgErr9AjuKuZdzCXd6atSrzKK`, a function-call key on the vault that can call `anchor` and nothing else ([transaction](https://nearblocks.io/txns/CFhtVrCA3Cjumcx68kixLbR5r6Xo8Fp1PTueK8z968jb)).
- **Mandate 2.** The owner's own Base wallet, up to 1.00 USDC, 1 use, until 2026-11-20 ([transaction](https://nearblocks.io/txns/77cC8nMq6qWynU51FsPn8mkFAb3NEuDmEG7ZXjX6483g)).

Then the SDK ran three cycles on INV-M002. Each one wrote a signed ledger entry and anchored the ledger before the next began:

| Entry | Time (UTC) | Who proposed | What code decided |
| --- | --- | --- | --- |
| 0 | 07:17 | `z-ai/glm-5.3-flash`, an attested model in a TEE on NEAR AI Cloud, proposed `pay` with confidence 0.95 | Refused by the rule `mandate.payee_mismatch`. Nothing was sent |
| 1 | 07:22 | `Qwen/Qwen3.8-27B`, attested, proposed `pay` with confidence 0.9 | Refused the same way. Nothing was sent |
| 2 | 07:24 | No model | The code rules alone allowed it: all 14 rules passed |
| 3 | 07:24 | None: this entry records the payment | Spend 2, `burned`, transaction `BdN7oB76…rSQ9` |

**Why code refused the two proposals.** Both models proposed the right amount and the right Base address. Both also put the mandate's asset account, `base-0x833589fcd6edb6e08f4c7c32d4f71b54bda02913.omft.near` (Base USDC as a NEAR token), in the payee hint's `near_account` field. The SDK the owner ran, at commit `4ab41ca`, took any NEAR account in the hint as a contradiction for a mandate that pays a Base address (`payeeHintContradiction` in [`packages/core/src/policy.ts`](https://github.com/probarion/probarion/blob/main/packages/core/src/policy.ts)). The rule's words in entry 0: "invoice names NEAR account base-0x833589fcd6edb6e08f4c7c32d4f71b54bda02913.omft.near; the mandate pays base:0xB22EAcDf11177d6D635E8956BBbBdd54B3E6EB27". The rule is strict on purpose: here it cost two tries and no money. [Why spend has no payee](/docs/concepts/why-spend-has-no-payee#the-code-layer-refuses-a-contradicting-payee) explains the rule.

**Why the code rules alone decided the payment.** The owner ran the cycle a third time with no model. The SDK decided with the code rules alone, and every rule passed. Entry 2's body hash, `d64f0de77c38294cf103439e6b5b0c2623b96b114962afd50f5a3c553df2a336`, is the `decision_hash` the spend carries, so the spend points at its own decision.

## Run the verifier

The verifier checks the ledger file against the chain. It reads public mainnet data and signs nothing. Build the CLI from a clone, because the `--ledger` and `--invoices` options are newer than release 0.1.1 on npm:

```bash
git clone https://github.com/probarion/probarion
cd probarion
pnpm install
pnpm --filter "{packages/cli}..." build
```

Then run it live, with the committed ledger, the invoice text for A8, the repository's evidence for spend 1 and the recorded transactions:

```bash
node packages/cli/dist/bin.js --network mainnet --rpc https://rpc.mainnet.fastnear.com verify --vault v0.probarion.near --ledger docs/evidence/mainnet-v0/s1-2026-11-13/ledger-2026-11-13.jsonl --invoices docs/evidence/mainnet-v0/s1-2026-11-13 --evidence docs/evidence --proof docs/mainnet-proof.json
```

At 07:24:43 UTC on 2026-11-13 this run ended with these two lines ([the full output](https://github.com/probarion/probarion/blob/main/docs/evidence/mainnet-v0/s1-2026-11-13/verify-2026-11-13.txt)):

```text
8 passed, 0 failed, 0 unproven, 1 skipped
RESULT: PASS
```

What each check found:

- [Checks a, b and c](/docs/trust/verifier-checks#check-a): the 4 entries carry valid signatures by the ledger key, their hash links recompute from the zero link, and the 3 anchors on chain match the ledger.
- [Check d](/docs/trust/verifier-checks#check-d): spend 2 is bound to its own `allow` decision, entry 2, with the same invoice, mandate and amount. Spend 1 of 2026-11-11 is exempt: its decision is a file in the repository, from before the vault had a ledger.
- [Check e](/docs/trust/verifier-checks#check-e): the 2 attested decisions, entries 0 and 1, pass A1 to A7, and A8 passes on both with the invoice text. Entry 2 is reported as decided by code rules with no model, not failed.
- [Checks f and g](/docs/trust/verifier-checks#check-f): no full-access key, every key is the ledger key or the agent key, and no key is registered for the vault in `intents.near`.
- [Check h](/docs/trust/verifier-checks#check-h): spend 2 has one matched burn pair, the `ft_burn` memo and the vault's `mt_burn` for the spend's amount.
- [Check i](/docs/trust/verifier-checks#check-i) skips: no factory made this vault.

Without `--ledger`, checks c and d fail: the chain's anchors cover 4 entries, and spend 2's decision is in no entry. A live run passes while the chain's anchors cover the entries this file holds. When the vault anchors a later entry, use the ledger file that holds it.

To check the recorded run with no network, read the snapshot the verifier wrote at 07:24:42 UTC:

```bash
node packages/cli/dist/bin.js verify --offline docs/evidence/mainnet-v0/s1-2026-11-13/snapshot-2026-11-13.json --invoices docs/evidence/mainnet-v0/s1-2026-11-13
```

The Base side is not in the ledger: entry 3 records the burn on NEAR. To read the transfer with no key, ask Base's public RPC:

```bash
curl -s https://mainnet.base.org -H 'content-type: application/json' -d '{"jsonrpc":"2.0","id":1,"method":"eth_getTransactionReceipt","params":["0xc2df8f8799467834cdaed0e8f23638af49334483387560fd34ef360939e1ea71"]}'
```

It answers `"status":"0x1"` and `"blockNumber":"0x363070a"` (56821514), with one `Transfer` log on the USDC contract, from `0x2cff890f0378a11913b6129b2e97417a2c302680` to `0xb22eacdf11177d6d635e8956bbbbdd54b3e6eb27`, whose data ends in `f38e0`: 997600.

## What this does not do

- **It is a test, not a customer payment.** One payout of 1.00 USDC went to the owner's own Base wallet. It shows the cross-chain path works on mainnet for this vault. It does not show a business paying a supplier.
- **No mainnet payment had come from a model's proposal by 2026-11-13.** Spend 1 of 2026-11-11 was sent without the SDK, and spend 2 was decided by the code rules alone.
- **The model hint fix is a separate change.** A later change to `payeeHintContradiction` lets a model's hint name the mandate's own asset account for a Base or Solana payee. It is not part of the code this page was checked against, and this run used the code before it.
- **The two attested decisions were checked offline.** A1 to A8 passed, but `verify --online` has not run on them, so O1 and O2 have not checked their TDX quotes and GPU evidence. The TEE measurement is not pinned, so the record does not show which model image ran.
- **The contract checks the burn, not the arrival.** The vault's part ends with the burn on NEAR. The POA bridge releases the USDC on Base, and check 07 reads that from Base.
- **No console or proof page serves this vault.** Both serve testnet. The mainnet factory is not deployed, so no other mainnet vault can be created yet.
